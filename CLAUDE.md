## Hard rule: never destroy data without approval

Never run `migrate:fresh`, `migrate:refresh`, `migrate:reset`, `migrate:rollback`, `db:wipe`, or `db:seed` against the development database (`work_order`), and never run any other command that deletes or overwrites data (raw SQL that drops, truncates, or deletes; deleting `storage/app/attachments`; etc.), without the user's explicit approval **in the current conversation**. Approval from an earlier conversation, a plan, or "migrate:fresh is acceptable" in a task description does not count: ask right before running the command. `--env=testing` does **not** switch to the test database (there is no `.env.testing`; artisan falls back to `.env`, which is the dev database). Tests never need these commands: `RefreshDatabase` migrates the test database itself.

## Commands

The script names are the same in composer (backend) and npm (frontend):

| Task                 | Backend (`composer …`)                   | Frontend (`npm run …`)                         |
| -------------------- | ---------------------------------------- | ---------------------------------------------- |
| Test                 | `test` (Pest)                            | `test` (Vitest via `vp test`), `test:watch`    |
| Lint (fix / check)   | `lint` / `lint:check` (Rector)           | `lint` / `lint:check` (oxlint via `vp lint`)   |
| Format (fix / check) | `format` / `format:check` (Pint)         | `format` / `format:check` (oxfmt via `vp fmt`) |
| Typecheck            | `types:check` (PHPStan/Larastan level 7) | `types:check` (vue-tsc)                        |
| Everything           | `check`                                  | `check`                                        |

- `composer ci:check` runs `npm run check` and `composer check`. CI (`.github/workflows/tests.yml`) runs exactly this, so it must pass before pushing.
- `composer dev` (`php artisan dev`) starts `serve`, `queue:listen`, `pail`, and `vite` together.
- `composer setup` runs a first-time install: `.env`, key, migrate, npm install, build. Postgres must be running first, with the `work_order` database created.
- Single backend test: `php artisan test --compact --filter='test name'` or `php artisan test --compact tests/Feature/Auth/AuthenticationTest.php`.
- Single frontend test: `npx vp test resources/js/composables/useInitials.test.ts` or `npx vp test -t 'test name'`.

## Git workflow

Always create the feature branch before making any change; never work directly on `main`. Each FLOW.md step is one branch and one PR (e.g. `feat/wo-v2-step4-daily-reports`).

Frontend tooling is **Vite+** (`vite-plus`, CLI `vp`). It bundles Vite, Vitest, oxlint, and oxfmt. Their config lives in `vite.config.ts` under the `test`, `lint`, and `fmt` blocks, not in separate eslint/prettier/vitest config files. In test files, import test APIs from `vite-plus/test`, not `vitest`.

## Architecture

**Request → page flow.** Routes in `routes/web.php`, `routes/settings.php`, and `routes/admin.php` (prefix `admin`, names `admin.*`) render Inertia pages, by name, from `resources/js/pages/`. Simple pages use `Route::inertia()`. `HandleInertiaRequests` shares these props on every page:

- `name`
- `auth.user`
- `auth.permissions` (the user's permission names, including those granted through roles, minus internal-only ones for IC users)
- `auth.isClient` (whether the user works for a client company, see Companies and isolation)
- `pendingRegistrations` (pending self-registrations for the Pendaftaran sidebar badge; null unless the user may review them)
- `displayTimezone` (see Dates and time)
- `sidebarOpen` (read from the `sidebar_state` cookie)

**Layouts are assigned by page name in `resources/js/app.ts`, not inside pages:**

- `ErrorPage` gets no layout.
- `auth/*` pages get `AuthLayout`.
- `settings/*` pages get `AppLayout` with `settings/Layout` nested inside.
- Every other page gets `AppLayout`.

Put new pages in the directory that gives them the right layout.

**Auth is Laravel Fortify (headless).** Fortify registers the auth routes and controllers. `FortifyServiceProvider` maps its views to Inertia pages (`auth/Login`, etc.), and password reset goes through `app/Actions/Fortify`. `registration` and `resetPasswords` are enabled in `config/fortify.php` (registration is described below). There is no self-delete. Admins create users in `Admin\UserController` with the default password from `DEFAULT_USER_PASSWORD` (`config('auth.default_user_password')`; creating users fails if it's unset), and no email is sent. Such users get `must_change_password = true`, and `EnsurePasswordIsChanged` (web group) keeps them on Settings › Security until they set their own password. Changing the password there or through forgot-password clears the flag. Login goes through `Fortify::authenticateUsing` and refuses inactive users. `EnsureUserIsActive` (web group) logs out a session whose user was deactivated. Soft-deleted users are never found by the user provider, so their login and sessions fail with no extra code. Two-factor auth and email verification are **off**: the `users` table has no 2FA columns, and tests for those features call `$this->skipUnlessFortifyHas(...)` (defined in `tests/TestCase.php`), so they show as skipped. Validation rules shared between Fortify actions and settings controllers live in `app/Concerns/*ValidationRules.php`.

**Self-registration with admin approval (FLOW.md §3), Unggul staff only.**

- **Registering.** `/register` goes through `App\Actions\Fortify\CreateNewUser`. It takes name, email, password, and department; no company is chosen. The email's domain must be exactly one of an active **executor** company's `email_domains` (`Company::allowsEmailDomain()`, case-insensitive, no subdomains; IC domains are refused, since IC never logs in), and that domain's company is the one the department must be an active department of (`CreateNewUser::registrableCompanies()`).
    - The account is created with `account_status = pending`, no roles, no forced password change, and `registered_at` set; nothing else in the request is read.
    - It logs one `registered` entry (IP included) instead of `created`, and the new user is signed in.
    - The page gets only `App\Support\RegistrationOptions` (active executor companies that have a domain: id, name, domains; their active departments: id, code, name, company_id); the page picks the company from the typed email and offers only its departments. `RegistrationTest` pins these keys, because the page is public.
- **Limiter and kill switch.** `register.store` uses the named limiter `registration` (5 a minute and 20 an hour per IP). Fortify has no setting for it, so `FortifyServiceProvider::configureRegistrationRoutes()` adds the middleware to Fortify's routes.
    - `REGISTRATION_ENABLED=false` (`config('registration.enabled')`, `EnsureRegistrationIsEnabled`) answers 404 on `/register` and hides "Daftar" on the login page. **This is the first response to a wave of spam registrations**; pending accounts stay reviewable.
- **Review state.** `users.account_status` (`App\Enums\AccountStatus`: pending, approved, rejected; not fillable; default approved, so admin-created and older accounts are approved) is separate from `is_active` (deactivation).
    - `EnsureAccountIsApproved` (web group) sends a pending or rejected account from every route except `registration.status` and `logout` to `registration.status` (`auth/RegistrationStatus`), which shows the review state and, when rejected, the reason.
    - Postgres checks the status values and that a rejection has a reason.
- **Pendaftaran** (`Admin\RegistrationController`, `admin.registrations.*`, permissions `registrations.view|approve|reject`, internal-only, admin by default) lists self-registrations by state.
    - Approve (`ApproveRegistration`, `ApproveRegistrationRequest`) grants at least one role that fits the company and never one holding `roles.manage`, so never admin: that stays on the Users page. The department may be corrected within the same company. Rejected registrations may be approved later (re-review).
    - Reject (`RejectRegistration`) needs a reason (max 500), pending only.
    - Both lock the row and answer a registration reviewed meanwhile with an error toast (`RegistrationNotReviewable`), and log one `registration_approved`/`registration_rejected` entry (status, roles, department, reason).
    - The Users page shows the review state in its Status column and filter (`pending`, `rejected`) and refuses roles for accounts under review.
- **Out of scope.** Email verification waits for mail (FLOW.md §11); domain matching and admin approval are the safeguards.

**Authorization is data-driven (spatie/laravel-permission).** Roles and their permissions live in the database and admins edit them on the Role page. Code only checks permissions, never role names. The exception is the `admin` role (`App\Enums\SystemRole`): it always holds every permission, belongs to the executor company, and cannot be renamed, reduced, or deleted. **Roles have a stable slug and a display label:** `roles.name` is the slug (`admin-wo`) that seeders, tests, helpers, and the audit log use; `roles.label` ("Admin WO", required on the Role page, nullable in the table) is what the UI shows (Role page, user list and form, Pendaftaran, badges) through `App\Support\RoleLabel` (`of()`, `option()` giving `{name, label}`; a role without a label shows its slug). Role changes log the label too. Permission names are cases of `App\Enums\Permission` (`resource.action`). To add one, add a case, check it in a policy, and re-run `php artisan db:seed --class=RolePermissionSeeder`, which syncs admin to all permissions but leaves other roles alone. Policies call `$user->checkPermissionTo(...)`, not `hasPermissionTo()`, which throws for unknown permissions. The frontend hides menus and buttons with `useCan()` and the `permission` field of `NavItem`, but that is only a hint: every endpoint still authorizes on the server. In tests, `userWithPermissions(...)`, `userWithRole('admin-wo')` (a seeded role by slug), and `adminUser()` from `tests/Pest.php` create authorized users.

**Companies and isolation (docs/FLOW.md §2, §3, §6).** `Company` (master data: code, name, `is_client`, `email_domains`, active/deleted) groups departments; every department has one (`departments.company_id`), every user has a department (`users.department_id` is NOT NULL), so a user's company is their department's. Client companies (IC) request work orders; the executor (Unggul) carries them out. **FLOW.md v2: IC never logs in.** IC departments are requester data only, registration is Unggul-only, and no initial role fits client users; the isolation below stays as a safeguard (and for a possible later read-only IC access). `User::isClient()` answers which side a user is on.

- **Guards.** A company's `is_client` cannot change once it has departments (deleted ones included); a department cannot move to another company once it has users or work orders; a company with departments cannot be deleted. Email domains are lowercase hostnames, unique across companies (for registration, FLOW.md step 1b).
- **Roles fit a company.** `roles.company_scope` (`App\Enums\CompanyScope`: `client`, `executor`, or null for any) is set on the Role page. Users may only hold roles that fit their company (`UserManagementValidationRules::roleFitCheck()`, on the submitted roles or, when roles are not sent, the current ones); a role's scope cannot change while holders would stop fitting; only executor-scoped roles may hold internal-only permissions (a role for "any" company could reach IC users), on the Role page (`RoleValidationRules::companyScopeChecks()`) and in `RolePermissionSeeder` (which throws otherwise). A role both sides need with different rights is split into a shared role and an executor role (e.g. an Unggul-only viewer with `departments.view` is its own executor role, not `viewer`). Initial roles (FLOW.md v2 §3, all executor-scoped, slug → label): `admin-wo` Admin WO, `lead-operational` Lead Operational, `pic-timesheet` PIC Timesheet, `rental` Rental, `direktur` Direktur, `finance` Finance, `viewer` Viewer, and `admin` Admin Sistem. v1 mapping: koordinator → Admin WO, pelaksana → Lead Operational (accept/reject) and PIC Timesheet, keuangan → Finance; `pemohon` is gone.
- **Internal-only permissions** (`Permission::isInternalOnly()`: departments, users, roles, registrations, categories, companies, activity log, and every `work-orders.*` permission except `work-orders.view`) are never held by IC users: `User::hasPermissionTo()` and `getAllPermissions()` drop them, whatever role or direct grant gives them, so every policy and the shared `auth.permissions` follow.
- **IC isolation.** Every route in `routes/admin.php` has the `internal` middleware (`EnsureInternalUser`), which answers 404 to IC users. Any new route that manages users, roles, master data, registrations, or the activity log goes in that group; `tests/Feature/Isolation/ClientIsolationTest.php` scans the router for such routes and calls every `admin.*` route as IC users (plain, with every permission, with the admin role), and checks that IC users' WO list, detail, and dashboard props carry no Unggul or other-IC data (create and edit answer 403: IC users never create or edit). Sidebar groups marked `internal` are hidden from IC users (`visibleNavGroups()` reads the shared `auth.isClient`).
- **Tests.** `icUser(...)` and `unggulUser(...)` in `tests/Pest.php` create users of a new client or executor department; `userWithPermissions()`, `userWithRole()`, and `adminUser()` are executor users. `DepartmentFactory` defaults to an executor company (`->client()` for IC); `UserFactory` creates a department. `WorkOrderFactory` defaults to a draft without a target, entered by a new executor user for a contact (`requester_name`) of a new IC department; states `by($user)` (who entered it), `requestedBy($department)`, `targeting($department)`, `submitted()` (a number; the target stays as set), `rejected()`, `inProgress()` (Pelaksanaan), `inReview()`, `awaitingBastApproval()`, `bastApproved()`, `closed()` (Belum ditagih), `billed()` (Ditagih), `paid()` (Lunas), `cancelled()`.

**Wayfinder.** `resources/js/actions/`, `resources/js/routes/`, and `resources/js/wayfinder/` are gitignored. The Vite plugin (`formVariants: true`) generates them from Laravel routes and controllers. Use them instead of hardcoded URLs. After changing routes, the dev server regenerates them; otherwise run `php artisan wayfinder:generate --with-form` (without the flag the `.form()` variants disappear and `types:check` fails).

`/` only redirects: to the dashboard when signed in, otherwise to login.

**App shell.** The sidebar (`components/AppSidebar.vue`) is a list of `navGroups` (Dashboard, Work Order, Master Data, Administrasi). Each item names the `permission` that shows it, `visibleNavGroups()` drops groups left empty, and groups marked `internal` (Master Data, Administrasi) never show to IC users. The topbar (`AppSidebarHeader.vue`) holds only the sidebar toggle, `ThemeToggle`, and the avatar `UserMenu`. Every page is one `components/PagePanel.vue`: serif h1 left, the page's breadcrumbs right (the layout `provide`s its `breadcrumbs` layout prop through `composables/usePageBreadcrumbs.ts`), an optional `meta` slot under the title, then the content as parts split by `border-b`, never boxes of their own. A group label crumb such as `{ title: 'Master Data' }` has no `href`. List pages stack `StatStrip.vue` (only where the numbers are useful: work orders, users, dashboard), `ListToolbar.vue` (primary action left, filters right; lists with many filters use `components/list-filters/FilterToolbar.vue` instead, see docs/DESIGN.md › Toolbar filter), then a `Table` with `panelTableClass` (`lib/panel.ts`). Rows are `ClickableRow.vue`: a click anywhere but a link, button, control, or menu item opens the record, and the main cell's link or button is the keyboard route to the same place. Row actions go in `RowActionsMenu.vue` (three dots); people show as `PersonName.vue`; forms end with `FormFooter.vue` (Simpan, Batal, right-aligned). Empty tables use `components/EmptyState.vue` inside `TableEmpty`: "Belum ada …" plus the create action when `isFiltering(props.filters)` is false, otherwise "Tidak ada … yang cocok" plus a "Hapus filter" link to the bare index URL. `DashboardController` serves the dashboard: its stat strip is "Menunggu Diterima" (Diajukan), "Pelaksanaan" (with a hint line "N belum lapor hari ini", `WorkOrder::missingDailyReport()`, not part of Terlambat), "Menunggu Pembayaran" (Closed WOs whose payment is Ditagih, linking to `payment=ditagih`), and "Terlambat" (`WorkOrder::overdue()`, with a hint line splitting it into "lewat target" and "lewat jatuh tempo" through `overdue($deadline)`), deferred counts over the WOs the user may see. `lib/dashboardMetrics.ts` builds the cards; each links to the list with the same filter (`StatItem.href`). Below the strip, side by side on desktop: "Ringkasan Pengajuan" (`WorkOrderRequestOverview`, `components/dashboard/RequestOverviewChart.vue`: WOs created per WITA day, grouped in the PostgreSQL query and zero-filled, stacked by current status, `?period=7|30`, anything else falls back to 7) and "WO Mendesak" (`UrgentWorkOrders.vue`: up to 5 active (`isActive()`) mendesak WOs with their status badge, in flow order and then oldest submission first, "Lihat semua" to the list with `urgency=mendesak&status=aktif`, which shows the same set). Both use `visibleTo()` and are deferred props. The chart is shadcn-vue `chart` (`@unovis/vue`); series colours come from `statusChartColor()`, per status with the tone as fallback (docs/DESIGN.md › Status Work Order). Below them, "WO Terbaru" (`components/dashboard/RecentWorkOrders.vue`, every user with `viewAny` WorkOrder) lists the 8 visible WOs with the latest activity (`updated_at`, see Work Order module › Last activity), with the WO list's row pattern (`components/work-orders/WorkOrderTitleCell.vue`, `ClickableRow`, no row actions) and "Lihat semua" to the list with `sort=diperbarui`. "Aktivitas terbaru" (audit log, `activity-log.view` only) stays below it: WO Terbaru is work items, Aktivitas terbaru is the audit trail.

**Error pages.** Outside debug mode, `Inertia::handleExceptionsUsing()` in `bootstrap/app.php` renders `pages/ErrorPage.vue` for 403, 404, 419, 500, and 503 (JSON requests still get JSON). With `APP_DEBUG=true` you see Laravel's stack trace page instead, so set it to `false` locally to view them.

**Localization.** The UI is Indonesian (`APP_LOCALE=id`). Framework messages live in `lang/id/*.php` and `lang/id.json`, published by `laravel-lang/lang` (dev dependency; refresh with `php artisan lang:update`) and excluded from Pint. Validation attribute names (`kode`, `nama`, …) are in the `attributes` key of `lang/id/validation.php`; add new form fields there. Write app strings in Indonesian directly, e.g. `__('Profil diperbarui.')`.

**Dates and time.** Store UTC, convert only at the edges:

- `app.timezone` stays `UTC`; timestamps are stored and serialized (ISO 8601) in UTC.
- The display timezone is WITA: `DISPLAY_TIMEZONE` (`config('app.display_timezone')`, default `Asia/Makassar`), shared to the frontend as `displayTimezone`.
- Frontend display goes through `resources/js/lib/format.ts` (`useFormatDate()` in components): `25 Sep 2026 10:15`, `25 Sep 2026`. Never call `toLocaleString()` or `Intl` directly in components.
- Server-written text (toasts, later exports/PDF) uses `App\Support\DisplayDate::dateTime()`/`date()`, which produce the same strings; date-only values use `DisplayDate::calendarDate()` (never converted, like `formatCalendarDate()`).
- User-entered dates used as filters become UTC bounds through `DisplayDate::startOfDayUtc()`/`endOfDayUtc()` (see `ActivityLogController::index`), so a 07:30 WITA entry is found under its WITA day.
- Date-only values (e.g. future WO due dates) use `DATE` columns and are never timezone-converted.

**Flash toasts.** On the backend, call `Inertia::flash('toast', ['type' => 'success', 'message' => ...])`. On the frontend, `resources/js/lib/flashToast.ts` listens for the router `flash` event and shows the message with `vue-sonner`.

**Audit trail (spatie/laravel-activitylog v5).** Everything goes to the `activity_log` table, readable at Admin › Log Aktivitas (`Admin\ActivityLogController`, permission `activity-log.view`, admin only).

- **Model changes** (log `audit`): models use `App\Concerns\LogsModelActivity`, which logs created, updated, deleted, and restored with only the fillable attributes that changed. An update that flips `is_active` is logged as `activated`/`deactivated`. Override `activityLogOptions()` to ignore housekeeping columns (see `User`).
- **Changes model events can't see**, such as pivot syncs (a user's roles, a role's permissions): call `logAuditChange()` from `App\Concerns\LogsAuditChanges` with the state before and after. It logs only the keys that changed, in the same shape as model changes.
- **Auth events** (log `auth`): `App\Listeners\RecordAuthActivity` (event discovery) plus `App\Concerns\LogsAuthActivity` log login, logout, failed login (email tried and IP, no causer), password changes, and resets. Because each failed login writes a row, the `login` rate limiter caps attempts both per email+IP (5/min) and per IP (30/min).
- **Never log secrets.** `password`, `remember_token`, and the 2FA columns are excluded globally in `config/activitylog.php`. `Illuminate\Auth\Events\Failed` carries the typed password in `credentials`, so read only `email` from it.
- Event names and their labels live in `App\Enums\AuditEvent`, and subject labels in `App\Enums\AuditSubject`. `ActivityResource` turns an entry into labelled before/after rows.
- **Retention.** `activitylog:clean` runs daily (`routes/console.php`) and keeps `ACTIVITYLOG_CLEAN_AFTER_DAYS` days (default 365). Production needs the scheduler running (`schedule:run` in cron).

**Appearance (light/dark).** `components/ThemeToggle.vue` (app header and auth pages) flips light/dark; Settings › Tampilan also offers "Sistem". The `appearance` cookie is read server-side by `HandleAppearance` and client-side by `composables/useAppearance.ts`. The `appearance` and `sidebar_state` cookies are deliberately left unencrypted in `bootstrap/app.php` so the frontend can read them.

## Work Order module

The v2 status flow of FLOW.md §5 with cancellation (§5.2), daily reports (§7), the payment track of closed WOs (§10), and rich-text comments with images and documents (§9), and the BAST: templates, generation, and approval (§8, §9, see BAST below). Out of scope so far: notifications, and for comments @mentions and a recipient field.

- **Statuses (FLOW.md §5).** `app/States/WorkOrder/` (spatie/laravel-model-states) holds every status and every allowed transition, and nothing else defines them: Draft → Diajukan → Pelaksanaan → Review Dokumen → Approval BAST → BAST Disetujui → Closed, Diajukan → Ditolak → Diajukan (resubmission, same number), Review Dokumen → Pelaksanaan (returned for revision), and Dibatalkan from Draft, Diajukan, Ditolak, Pelaksanaan, and Review Dokumen. Closed and Dibatalkan are final. Stored names: `draft`, `diajukan`, `ditolak`, `pelaksanaan`, `review_dokumen`, `approval_bast`, `bast_disetujui`, `closed`, `dibatalkan`. Each state carries its label, badge `tone` (docs/DESIGN.md: secondary, warning, destructive, info, review, approval, approved, success, muted), its outgoing `transitions()` (below), `waitingMessage()`, and flags: `isEditable` (Draft, Ditolak), `isDeletable` (Draft only, so a numbered WO is cancelled, never deleted), `assignsNumber` (Diajukan), `acceptsComments` (all but Dibatalkan, and Closed once paid), `attachmentPermissions` (which permission may change which collection), `deadline` (see Overdue), `requiresNumber`, and `isActive` (abstract: submitted and not final, i.e. Diajukan through BAST Disetujui; `WorkOrderStatusFlowTest` checks it against `requiresNumber()` and the outgoing transitions). Every new status must set all of them. **`requiresNumber()` is true for every status after the first submission** and false for Draft and Dibatalkan; **the database backs it** with `work_orders_submitted_number_check`, because visibility reads "has a number" as "was submitted"; `WorkOrderStatusFlowTest` fails if a state with `requiresNumber()` is missing from it. `waitsOn()` is derived: the permissions of the status's transitions other than cancelling (Closed: `bill` while Belum ditagih, `confirm-payment` while Ditagih). The UI gets statuses from `WorkOrderStatus::options()` and each WO's available transitions from the server, so changing the flow means editing that folder, the dashboard's cards (`workOrderCounts()` and `lib/dashboardMetrics.ts`), and tests. The list's status filter also takes the group `aktif` (`WorkOrderStatus::GROUP_ACTIVE`, `namesFor()`), every status whose `isActive()` is true, so a new active status joins it and "WO Mendesak" without other changes. `RetiredStatusReferencesTest` fails on any identifier of the v1 statuses (Dikerjakan, Penagihan, Selesai) or sides; the step 3 migration's refusal is the one exception.
- **Transitions and permissions (FLOW.md §5.1, §5.2).** Each status lists its outgoing changes in the static `transitions()` as `WorkOrderTransition`s (destination, permission, button label, `requiresNote`/`noteLabel`, `isDestructive`, `requirements`, `effects`); `WorkOrderStatus::config()` builds the state machine from them (static because a state's constructor reads the config). Everything belongs to the transition, not the destination: Pelaksanaan is entered by Lead Operational (approve) and by Rental (return, note), Dibatalkan by Admin WO or Lead Operational. Permissions, each internal-only (seeded roles in parentheses): `work-orders.submit` Draft/Ditolak → Diajukan (Admin WO; "Ajukan ulang" from Ditolak); `work-orders.approve` Diajukan → Pelaksanaan or Ditolak (note) (Lead Operational); `work-orders.submit-review` Pelaksanaan → Review Dokumen (PIC Timesheet); `work-orders.review` Review Dokumen → Pelaksanaan (note "Data yang perlu dilengkapi") or Approval BAST (Rental); `work-orders.approve-bast` Approval BAST → BAST Disetujui (Direktur, approve only); `work-orders.close` BAST Disetujui → Closed (Admin WO); `work-orders.cancel` Draft/Diajukan/Ditolak → Dibatalkan (Admin WO, note); `work-orders.cancel-execution` Pelaksanaan/Review Dokumen → Dibatalkan (Lead Operational, note); nobody cancels from Approval BAST on. `WorkOrderPolicy::transition($user, $wo, $to)` allows the holder of the current status's permission for that change (never a client company user); `changeStatus` (holding any transition permission, `WorkOrderStatus::transitionPermissions()`) makes a change the status does not allow a validation message rather than a 403. The detail page gets only the transitions the user may perform, `waitingFor` (the status's `waitingMessage()` for users holding none of its `waitsOn()` permissions), and `statusNote` (the note of the change that entered the current status, when that change requires one: rejected, returned, cancelled). `WorkOrderTransitionMatrixTest` runs every role (plus an internal user without a role and an IC user holding every permission) against every status and destination, and every payment action against every payment status.
- **Transitions run** only through `App\Actions\WorkOrders\TransitionWorkOrder`, which in one transaction locks the WO, refuses a change the status does not allow (`CouldNotPerformTransition`) or one without a required note, checks the transition's requirements, assigns the number if the new status `assignsNumber()` and it has none yet (so a resubmission keeps it), transitions, writes a `work_order_status_histories` row (from, to, user, note), logs `AuditEvent::StatusChanged`, and runs the transition's effects. `status` and `number` are not fillable, so model events never log them twice. Creation writes the first history row (`null → draft`).
- **Transition requirements and effects.** `App\Actions\WorkOrders\Transitions\TransitionRequirement` (`unmetReason()`: a message, or null when met; `TransitionWorkOrder` checks it under the lock before the status changes and refuses with the message on `status`, and the detail page sends it as the transition's `blocked_reason`, so the button is disabled with the reason below it) and `TransitionEffect` (`handle()`, runs after it in the same transaction; an exception rolls it back), resolved from the container. Pelaksanaan → Review Dokumen requires `EnsureDailyReport` (see Daily reports). Review Dokumen → Approval BAST requires `EnsureActiveBastTemplate` and runs `GenerateBast`; Approval BAST → BAST Disetujui runs `ApproveBast` (see BAST). `WorkOrderTransitionHooksTest` pins where they are declared and how they run.

- **BAST (FLOW.md §8, §9).** Code in `app/Support/Bast/`, `app/Actions/BastTemplates/`, and the two transition effects.
    - **One template, immutable versions.** `BastTemplate` (exactly one row, `BastTemplate::current()`; a unique index on a constant holds it to one) has the editable `draft_html` and its images (collection `gambar`, PNG and JPEG only, `BAST_TEMPLATE_MAX_IMAGES` 3, `BAST_TEMPLATE_IMAGE_MAX_SIZE_KB` 1024, at most `max_side_px` 4000 pixels per side, read from the header by `AllowedAttachment` (`AttachmentCollection::$maxImageSide`) and checked again before embedding, so a small file cannot unpack into a huge bitmap; no SVG). `PublishBastTemplate` copies the sanitized draft into a new `BastTemplateVersion` (`version` per template, `html`, `images` jsonb: the images it shows as base64, so deleting an upload never changes a version, `published_by`, null for the seeder) and makes it the only active one (partial unique index on `is_active`); it refuses an empty draft or one equal to the latest version. `ActivateBastTemplateVersion` re-activates an older one (rollback). A version never changes: the model refuses and a Postgres trigger (`bast_template_versions_immutable`) rejects any update but `is_active`, and every delete. All three actions lock the template row and log on it (`bast_template_saved` without content, `bast_template_published`/`bast_template_activated` with `versi_aktif`).

Limits: 128 KB (`template_max_html_bytes`, checked before parsing) and 24 levels of nesting (`template_max_depth`, checked before sanitizing), which bound the sanitizer's cost. A value's line breaks become `<br>`.

- **Rich text (FLOW.md §9).** The editor is Tiptap (`components/work-orders/CommentEditor.vue`, extensions listed explicitly in `lib/commentEditor.ts`, no StarterKit): paragraphs, hard breaks, bold, italic, strike, inline code, bullet and ordered lists, blockquotes, links, and inline images; no headings, tables, colours, raw HTML, or embeds. **The server is the authority:** `App\Support\Comments\CommentHtml::sanitize()` runs on every write (symfony/html-sanitizer allowlist on PHP 8.4's HTML5 parser, then a DOM pass) and keeps only those elements; links only `http`, `https`, `mailto`, always `target="_blank" rel="noopener noreferrer nofollow"`; an image only when its `src` is exactly `/attachments/{uuid}` of the comment's own files or the author's pending uploads on this WO (anything else, including another WO's or another comment's upload, is dropped), with alt text defaulting to the file name. It returns the HTML, the plain text (limits, later previews and notifications), and the image uuids. Limits: 64 KB of HTML (`CommentHtml::MAX_HTML_BYTES`, checked before sanitizing), 5000 plain-text characters (`MAX_TEXT_LENGTH`), and a comment needs text, an image, or a document. `CommentHtml::forDisplay()` sanitizes the stored HTML again when the timeline is built, and `components/work-orders/CommentBody.vue` is **the only `v-html` in the app**; never render comment HTML anywhere else. `tests/Fixtures/comment-html.json` is the contract: `tests/Unit/CommentHtmlTest.php` (with the XSS and mutation-XSS payload suite) proves the server keeps each case unchanged, `resources/js/lib/commentEditor.test.ts` that the editor writes and reloads each unchanged; a new format needs a case there on both sides. Old plain-text comments were converted by a migration (`CommentHtml::fromPlainText()`: escaped, blank lines start paragraphs, single line breaks become `<br>`).
- **Comment files.** Inline images (JPG, PNG, WEBP; `WO_COMMENT_MAX_IMAGES` per comment, default 10, `WO_COMMENT_IMAGE_MAX_SIZE_KB` 5 MB) and documents (every `AttachmentType`; `WO_COMMENT_MAX_DOCUMENTS` 5, 10 MB), `config('work_order.comments')`. The editor uploads each file at once to `POST work-orders/{wo}/comment-uploads/{gambar|lampiran}` (`WorkOrderCommentUploadController`, authorized by `addComment`, refused once the status is read-only, limiter `wo-comment-upload`, JSON answer), which stores it through `AddAttachment` as a **pending upload** on the WO (collections `komentar_gambar`/`komentar_lampiran`, `AttachmentCollection::$holdsPendingUploads`: at most `WO_COMMENT_MAX_PENDING_UPLOADS` per uploader per WO, not logged, not counted as activity). Posting or editing claims them (`App\Support\Comments\CommentContent`, under the WO lock): images from the body, documents from `attachments[]` uuids (anything not the author's pending upload or the comment's own file is a validation error), moved onto the comment (`gambar`/`lampiran`) by updating their media rows; files an edit drops are deleted after the commit. **Deleting a comment deletes its files after the commit**; their names stay in the audit log. Pending uploads are shown only to their uploader (`WorkOrderPolicy::viewAttachment`); a comment's files follow the WO's `view` (`WorkOrderCommentPolicy::viewAttachment`, 404 for a deleted comment or WO); the generic attachment endpoints never change comment files. Abandoned uploads older than `WO_COMMENT_UPLOAD_PRUNE_HOURS` (default 24) are deleted by `work-orders:prune-comment-uploads`, scheduled hourly, so production needs the scheduler (docs/DEPLOY.md).
- **PROVISIONAL: comment rules.** A status whose `acceptsComments()` is false keeps its comments read-only: Dibatalkan, and Closed once its payment is Lunas (while Belum ditagih or Ditagih Finance coordinates billing there, FLOW.md §5.3). Authors may edit or delete their own comment only within `config('work_order.comments.edit_window_minutes')` (`WO_COMMENT_EDIT_MINUTES`, default 15); edited ones show "(diedit)", deleted ones stay in the timeline as "Komentar dihapus". Both rules are enforced in the actions (`CommentNotAllowed` → error toast), not the policy, because an open page can go stale. `RolePermissionSeeder::INITIAL_ROLES` grants `work-orders.comment` to every initial role except Viewer (fresh installs only).
- **Timeline.** The detail page's "Aktivitas" section (full width, below Dokumen) is `App\Support\WorkOrderTimeline`: status history and comments (deleted ones included) merged oldest first; at the same moment a status change comes first. Transition notes stay inside their status entry. `components/work-orders/WorkOrderTimeline.vue` renders it with the comment form at the bottom. A comment entry carries its body (sanitized again) and its documents (`attachments`); inline images open full size in a dialog, documents are `components/attachments/AttachmentRow.vue` rows like the Dokumen panel.
- **Last activity** is `updated_at`. Besides edits, it is bumped by status changes (the transition saves the WO), comments (posted, edited, deleted: `#[Touches]` on `WorkOrderComment`), and attachments (`AddAttachment`/`RemoveAttachment` touch the parent, so later collections such as the invoice count too; billing and confirming a payment touch the WO themselves). Touching logs nothing, because `LogsModelActivity` ignores a change to `updated_at` alone (`WorkOrderLastActivityTest`). Because a comment touches its WO, `lockAcceptingComments()` takes an update lock, not a shared one: two commenters upgrading shared locks deadlock (`WorkOrderCommentConcurrencyTest`, group `concurrency`).
- **Last-activity indexes.** `work_orders` has `(requester_department_id, updated_at)` and `(target_department_id, updated_at)` (the latter replaced the plain `target_department_id` index), for "WO Terbaru" and the "Terakhir diperbarui" sort within IC and executor visibility, next to `(requester_department_id, created_at)` for the default newest-first order.

## Attachments

Files on any model, through spatie/laravel-medialibrary. Work orders are the first user (see above).

- **Making a model attachable.** Implement `App\Support\Attachments\Attachable`, use `App\Concerns\HasAttachments`, and declare `attachmentCollections()`: one `AttachmentCollection` per collection (name, `maxFiles`, `maxSizeKb`, optional subset of `AttachmentType`s), with limits read from that module's config. The model must be in the morph map. Its policy needs `viewAttachment(User, Model, Media)` (viewing and downloading, usually its `view`), `addAttachment(User, Model, string $collection)`, and `deleteAttachment(User, Model, Media)`, all starting with the model's visibility check. Pass `AttachmentPanel::props($model, $collection, $user, $request)` to the page and render `components/attachments/AttachmentPanel.vue`; nothing else is model-specific.
- **Where the rules live.** Allowed types: `App\Enums\AttachmentType` (PDF, JPG, PNG, WEBP, DOCX, XLSX). SVG, HTML, and macro-enabled Office files are deliberately not cases, so no collection can accept them. `App\Support\Attachments\AttachmentTypeDetector` identifies a file by content (finfo), never by its name or the client's MIME type; for ZIP-family results it opens the package and accepts only a single `docx`/`xlsx` main part and no `vbaProject.bin` (libmagic reports docm/xlsm as docx/xlsx). Validation is `AttachmentCollection::fileRules()` (size + `App\Rules\AllowedAttachment`); `App\Actions\Attachments\AddAttachment` re-detects the type and checks the file count with the parent row locked, before anything is stored. It registers `DB::afterRollBack()` to delete the stored file, so a rollback in its own or the caller's transaction (e.g. `WorkOrderController::store` with several documents) leaves no orphan; a PHP process killed mid-request can still leave one, and there is no sweep job yet. Uploads are throttled to 30 a minute per user.
- **Private disk only.** Files go to the `attachments` disk (`storage/app/attachments`, no URL, `serve => false`; `MEDIA_DISK`). They are stored as `{media uuid}/{random uuid}.{detected ext}` (`AttachmentPathGenerator`); the original filename is kept only in `media.name`, for display and the download name. `media.mime_type` is the detected type and `media.uploaded_by` the uploader. Never generate a URL on the disk or use media-library's `getUrl()`.
- **Every file goes through `AttachmentController`.** `attachments.store` (`POST attachments/{alias}/{id}/{collection}`) resolves the parent by morph alias (404 unless it is `Attachable` and has the collection) and authorizes `addAttachment`; `attachments.show` (`GET attachments/{uuid}`) authorizes the parent's `viewAttachment`, so department visibility gives 404, and a deleted parent gives 404; `attachments.destroy` authorizes `deleteAttachment`. `show` sends the detected `Content-Type`, `X-Content-Type-Options: nosniff`, and `Cache-Control: private, no-store`; images and PDF are `inline` (unless `?download=1`), everything else is `attachment`.
- **Audit.** `AddAttachment`/`RemoveAttachment` log `AuditEvent::AttachmentAdded`/`AttachmentRemoved` on the parent with `lampiran` (filename) and `ukuran` (bytes, shown as "1,6 KB"), never file content; pending uploads (a collection with `holdsPendingUploads`) are not logged until the record that claims them logs them. `Media` does not use `LogsModelActivity`. Soft-deleting the parent keeps its files; only a force delete (never offered) would remove them.
- **Upload limits.** The size limit only works if PHP's `upload_max_filesize` and `post_max_size` and the web server's body limit (nginx `client_max_body_size`) are at least as large; `post_max_size` must also fit a create form with several documents (e.g. 10 × 10 MB). `MEDIA_MAX_FILE_SIZE_MB` (default 50) is media-library's hard ceiling above every collection limit.
- **Tests.** Fixtures in `tests/Fixtures/attachments/` (real files, excluded from formatting); `attachmentUpload($fixture, $clientName)` in `tests/Pest.php` disguises one type as another. Fake the disk with `Storage::fake('attachments')`.

## Master data module pattern

`Department` is the reference implementation. New master data (WO categories, vendors, etc.) copies it file for file. `User` follows the same rules with extra account logic.

- **Active vs deleted.** `is_active = false` means deactivated: the record stays in lists with a `StatusBadge` and can still be referenced. Soft delete (`SoftDeletes`) hides it from lists and dropdowns. It shows up only under "Tampilkan terhapus", which needs `*.restore`, with a Pulihkan action (`PATCH <resource>/{id}/restore`, route `->withTrashed()`). The UI never force-deletes. **Relationships from other modules to master data use `->withTrashed()`** so history still resolves.
- **Unique vs trashed.** Unique indexes still cover deleted rows. Use `Rule::unique(...)->withoutTrashed()` plus `App\Rules\NotTakenByTrashed`. That rule shows the "pulihkan" hint only to users who can `viewTrashed`, and everyone else gets the standard "taken" message. See `app/Concerns/DepartmentValidationRules.php`.
- **Delete guards.** Refuse deletes that would orphan live data with an error toast and `back()`, not an exception. Example: `DepartmentController::destroy` refuses while `$department->users()->exists()` and suggests deactivating instead.
- **Audit trail.** The model uses `LogsModelActivity` (and gets a morph alias, see Conventions). Controller writes that model events miss, such as pivot syncs, call `logAuditChange()`. Add the alias to `AuditSubject` (and to `withHistoryPanel()`), the label of any new attribute to `ActivityResource::FIELD_LABELS`, and new event names to `AuditEvent`. Index rows get a "Riwayat" icon button (`History`, shown with `useCan()('activity-log.view')`) that opens the shared `components/admin/ActivityHistorySheet.vue`.
- **Permissions and policy.** Add `App\Enums\Permission` cases `<resource>.view|create|update|delete|restore` (kebab-case plural resource). `app/Policies/DepartmentPolicy.php` maps them as follows: `viewAny`→`view`, `viewTrashed`/`restore`→`restore`, and `forceDelete` returns `false`. Every check uses `$user->checkPermissionTo(...)`.
- **Seeder.** `database/seeders/RolePermissionSeeder.php` creates every enum case with `findOrCreate`, calling `forgetCachedPermissions()` before and after (without the second call, `syncPermissions` can't see the new permissions). It then syncs `admin` to all permissions. Grants for other roles go in `INITIAL_ROLES`, which only applies when the role is first created.
- **Backend files.**
    - Model with an `inactive()` factory state and a `#[Scope] search` via `SearchesColumns`: `app/Models/Department.php`.
    - Shared rules trait: `app/Concerns/<Resource>ValidationRules.php`.
    - `Store`/`Update<Resource>Request` in `app/Http/Requests/Admin/`, with `authorize()` via the policy.
    - `app/Http/Controllers/Admin/<Resource>Controller.php`: `index` validates the filters, requires `viewTrashed` for `trashed=1`, returns `paginate(15)->withQueryString()` plus a `can` map; the other actions flash a toast.
    - Routes in `routes/admin.php`.
- **Frontend.**
    - Page: `resources/js/pages/admin/<resources>/Index.vue`, with `PagePanel`, `ListToolbar`, `ClickableRow` + `RowActionsMenu`, a group crumb plus its own crumb, and `EmptyState` for both empty cases (no `StatStrip` unless its numbers are useful). Small forms use a dialog in `components/admin/` (`DepartmentFormDialog.vue`); large forms use `Create`/`Edit` pages sharing a form component (`UserForm.vue`).
    - Filters: `composables/useListFilters.ts` (debounced search, `ALL` sentinel for selects, booleans sent as `1`).
    - Table: `components/ui/table`, `components/admin/TablePagination.vue`, `StatusBadge.vue`, and `ConfirmDialog.vue` for deletes.
    - Types go in `types/admin.ts`, and the sidebar entry in the right `navGroups` group of `AppSidebar.vue` with a `permission`.

## Conventions and gotchas

- **Morph map is enforced** (`Relation::enforceMorphMap()` in `AppServiceProvider`). Polymorphic columns (`model_has_roles`, `model_has_permissions`, `activity_log`, `media`) store short aliases such as `user` and `wo-category`, not class names. Every model used polymorphically must be registered there, or it throws `ClassMorphViolationException`. In tests, compare against `$model->getMorphClass()`, not `Model::class`.
- **Emails are case-insensitive.** `User` stores every email trimmed and lowercase (the `email()` mutator, `User::normalizeEmail()`), the unique index is on `lower(email)` (`users_email_lower_unique`, deleted accounts included), and lookups go through `User::withEmail()`. Form requests that validate an email normalize it in `prepareForValidation()` first, so the `unique` rules catch another casing as a validation error instead of an index violation; a new one must do the same.
- **Rate limits: always a named limiter, never a plain `throttle:N,1`.** A plain `throttle:N,1` keys only on the user, so every route using one shares one counter (10 uploads used to block the export). Define each limiter with `RateLimiter::for()` in `AppServiceProvider::configureRateLimiting()` (Fortify's `login` stays in `FortifyServiceProvider`) and attach it as `throttle:<name>`; today `password-update`, `registration` (per IP), `wo-export`, `wo-comment-post`, `wo-comment-change`, `wo-comment-upload`, `attachment-upload`, `wo-invoice`, `wo-daily-report`, `bast-template-preview`. `tests/Feature/RateLimitingTest.php` fails if any route uses a plain `throttle:N`.
- `resources/js/components/ui/*` is generated shadcn-vue code (`components.json`). Lint and format both ignore it, so add or replace components with the shadcn CLI instead of restyling them by hand.
- Rector (`rector.php`) deliberately skips `declare(strict_types=1)`, and skips `: void` on closures in `tests/`. The codebase doesn't use strict_types, so don't add it.
- PHPStan covers `app/`, `config/`, `database/`, `routes/`, and `bootstrap/app.php`. It does not cover `tests/`.
- **PHP 8.4 or later is required, including production.** `openspout/openspout` ^5 (the Excel export) needs it. PENDING: the production PHP version is not confirmed yet; if it is 8.3, switch to openspout ^4 and lower `composer.json`'s `php` constraint back to `^8.3`.
- The database is **PostgreSQL** in every environment. Locally it's the shared `postgres-dev` container from `~/Workspaces/databases/docker-compose.yml` (`docker compose up -d postgres` there), with the databases `work_order` (dev) and `work_order_test` (tests; set in `phpunit.xml`). CI runs a `postgres:16` service, and production uses its own server. Postgres `LIKE` is case-sensitive, so search through `App\Concerns\SearchesColumns` (ILIKE with escaped wildcards) instead of a raw `where(..., 'like', ...)`.
- Feature tests use `RefreshDatabase` through `tests/Pest.php`, so Postgres must be running before `composer test`.
- **Test database.** The suite uses `work_order_test` (`DB_DATABASE` in `phpunit.xml`; CI sets the same). `--parallel` runs use copies named `work_order_test_test_N`, and the `concurrency` group passes the same connection to its child processes (`concurrentProcessEnv()`). `Tests\TestCase::setUpTraits()` refuses to boot `RefreshDatabase` unless the connection's database ends in `_test` (or `_test_test_N`), because a `DB_DATABASE` exported in the shell overrides `phpunit.xml` (even with `force="true"`). Verified: a full parallel run plus the concurrency group leaves `work_order` untouched. To inspect the test database from artisan, prefix the command with `DB_DATABASE=work_order_test`, never `--env=testing`.
- **BACKLOG: Content-Security-Policy.** There is no CSP yet. Add an app-wide one (at least `img-src 'self' blob:`, no inline script) as defense in depth for rich comments, as a separate task: it affects the Vite dev server (HMR, `@vite` tags), Inertia's SSR head, and inline styles from reka-ui.
- **BACKLOG: comment sanitizing cost.** Sanitizing a maximally nested 64 KB comment body (`CommentHtml::sanitize()`, e.g. 8192 nested `<ul><li>`) costs about 0.8 s of CPU. Today that is bounded by the size cap (`CommentHtml::MAX_HTML_BYTES`, checked in the request before any lock) and the comment rate limits (`wo-comment-post`, `wo-comment-change`); revisit, e.g. with a nesting-depth cap, if either is relaxed.
- **KNOWN ISSUE: SSR hydration warnings.** Pages log Vue hydration mismatches in the browser console: reka-ui's generated IDs differ between server and client (e.g. `reka-dropdown-menu-trigger-v-7` vs `-v-0`, on the avatar menu and every `RowActionsMenu`, and `reka-popover-trigger-*` on the WO list's Filter button), and the sidebar toggle icon's path differs (the server can't know the sidebar/viewport state). They are check-only (the DOM isn't patched) and predate the comments feature; not fixed yet.
- `.npmrc` sets `ignore-scripts=true`, so npm packages' install scripts don't run.
