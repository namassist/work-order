# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Laravel 13 + Inertia v3 + Vue 3 (TypeScript) + Tailwind v4 + shadcn-vue (reka-ui), built from the Laravel Vue starter kit. Framework/package conventions (Boost MCP tools, Pest, Pint, Inertia, Wayfinder) live in `AGENTS.md`. It is regenerated by `php artisan boost:update` (runs on `composer update`), so don't hand-edit it.

## Commands

The script names are the same in composer (backend) and npm (frontend):

| Task                 | Backend (`composer …`)                   | Frontend (`npm run …`)                         |
| -------------------- | ---------------------------------------- | ---------------------------------------------- |
| Test                 | `test` (Pest)                            | `test` (Vitest via `vp test`), `test:watch`    |
| Lint (fix / check)   | `lint` / `lint:check` (Rector)           | `lint` / `lint:check` (oxlint via `vp lint`)   |
| Format (fix / check) | `format` / `format:check` (Pint)         | `format` / `format:check` (oxfmt via `vp fmt`) |
| Typecheck            | `types:check` (PHPStan/Larastan level 7) | `types:check` (vue-tsc)                        |
| Everything           | `check`                                  | `check`                                        |

- `composer ci:check` runs `npm run check` and `composer check`. CI (`.github/workflows/tests.yml`) runs exactly this, so it must pass before pushing.
- `composer dev` (`php artisan dev`) starts `serve`, `queue:listen`, `pail`, and `vite` together.
- `composer setup` runs a first-time install: `.env`, key, migrate, npm install, build. Postgres must be running first, with the `work_order` database created.
- Single backend test: `php artisan test --compact --filter='test name'` or `php artisan test --compact tests/Feature/Auth/AuthenticationTest.php`.
- Single frontend test: `npx vp test resources/js/composables/useInitials.test.ts` or `npx vp test -t 'test name'`.

Frontend tooling is **Vite+** (`vite-plus`, CLI `vp`). It bundles Vite, Vitest, oxlint, and oxfmt. Their config lives in `vite.config.ts` under the `test`, `lint`, and `fmt` blocks, not in separate eslint/prettier/vitest config files. In test files, import test APIs from `vite-plus/test`, not `vitest`.

## Architecture

**Request → page flow.** Routes in `routes/web.php`, `routes/settings.php`, and `routes/admin.php` (prefix `admin`, names `admin.*`) render Inertia pages, by name, from `resources/js/pages/`. Simple pages use `Route::inertia()`. `HandleInertiaRequests` shares these props on every page:

- `name`
- `auth.user`
- `auth.permissions` (the user's permission names, including those granted through roles)
- `displayTimezone` (see Dates and time)
- `sidebarOpen` (read from the `sidebar_state` cookie)

**Layouts are assigned by page name in `resources/js/app.ts`, not inside pages:**

- `ErrorPage` gets no layout.
- `auth/*` pages get `AuthLayout`.
- `settings/*` pages get `AppLayout` with `settings/Layout` nested inside.
- Every other page gets `AppLayout`.

Put new pages in the directory that gives them the right layout.

**Auth is Laravel Fortify (headless).** Fortify registers the auth routes and controllers. `FortifyServiceProvider` maps its views to Inertia pages (`auth/Login`, etc.), and password reset goes through `app/Actions/Fortify`. Only `resetPasswords` is enabled in `config/fortify.php`. There is no public registration and no self-delete: admins create users in `Admin\UserController` with the default password from `DEFAULT_USER_PASSWORD` (`config('auth.default_user_password')`; creating users fails if it's unset), and no email is sent. Such users get `must_change_password = true`, and `EnsurePasswordIsChanged` (web group) keeps them on Settings › Security until they set their own password. Changing the password there or through forgot-password clears the flag. Login goes through `Fortify::authenticateUsing` and refuses inactive users. `EnsureUserIsActive` (web group) logs out a session whose user was deactivated. Soft-deleted users are never found by the user provider, so their login and sessions fail with no extra code. Two-factor auth and email verification are **off**: the `users` table has no 2FA columns, and tests for those features call `$this->skipUnlessFortifyHas(...)` (defined in `tests/TestCase.php`), so they show as skipped. Validation rules shared between Fortify actions and settings controllers live in `app/Concerns/*ValidationRules.php`.

**Authorization is data-driven (spatie/laravel-permission).** Roles and their permissions live in the database and admins edit them on the Role page. Code only checks permissions, never role names. The exception is the `admin` role (`App\Enums\SystemRole`): it always holds every permission and cannot be renamed, reduced, or deleted. Permission names are cases of `App\Enums\Permission` (`resource.action`). To add one, add a case, check it in a policy, and re-run `php artisan db:seed --class=RolePermissionSeeder`, which syncs admin to all permissions but leaves other roles alone. Policies call `$user->checkPermissionTo(...)`, not `hasPermissionTo()`, which throws for unknown permissions. The frontend hides menus and buttons with `useCan()` and the `permission` field of `NavItem`, but that is only a hint: every endpoint still authorizes on the server. In tests, `userWithPermissions(...)` and `adminUser()` from `tests/Pest.php` create authorized users.

**Wayfinder.** `resources/js/actions/`, `resources/js/routes/`, and `resources/js/wayfinder/` are gitignored. The Vite plugin (`formVariants: true`) generates them from Laravel routes and controllers. Use them instead of hardcoded URLs. After changing routes, the dev server regenerates them; otherwise run `php artisan wayfinder:generate`.

`/` only redirects: to the dashboard when signed in, otherwise to login.

**App shell.** The sidebar (`components/AppSidebar.vue`) is a list of `navGroups` (Dashboard, Work Order, Master Data, Administrasi). Each item names the `permission` that shows it, and `visibleNavGroups()` drops groups left empty. The topbar (`AppSidebarHeader.vue`) holds only the sidebar toggle, `ThemeToggle`, and the avatar `UserMenu`. Every page is one `components/PagePanel.vue`: serif h1 left, the page's breadcrumbs right (the layout `provide`s its `breadcrumbs` layout prop through `composables/usePageBreadcrumbs.ts`), an optional `meta` slot under the title, then the content as parts split by `border-b`, never boxes of their own. A group label crumb such as `{ title: 'Master Data' }` has no `href`. List pages stack `StatStrip.vue` (only where the numbers are useful: work orders, users, dashboard), `ListToolbar.vue` (primary action left, filters right), then a `Table` with `panelTableClass` (`lib/panel.ts`). Rows are `ClickableRow.vue`: a click anywhere but a link, button, control, or menu item opens the record, and the main cell's link or button is the keyboard route to the same place. Row actions go in `RowActionsMenu.vue` (three dots); people show as `PersonName.vue`; forms end with `FormFooter.vue` (Simpan, Batal, right-aligned). Empty tables use `components/EmptyState.vue` inside `TableEmpty`: "Belum ada …" plus the create action when `isFiltering(props.filters)` is false, otherwise "Tidak ada … yang cocok" plus a "Hapus filter" link to the bare index URL. `DashboardController` serves the dashboard: "Total WO" and "Menunggu Persetujuan" are deferred counts over the WOs the user may see; "Dalam Pengerjaan" and "Terlambat" stay "Segera hadir" until those WO stages exist.

**Error pages.** Outside debug mode, `Inertia::handleExceptionsUsing()` in `bootstrap/app.php` renders `pages/ErrorPage.vue` for 403, 404, 419, 500, and 503 (JSON requests still get JSON). With `APP_DEBUG=true` you see Laravel's stack trace page instead, so set it to `false` locally to view them.

**Localization.** The UI is Indonesian (`APP_LOCALE=id`). Framework messages live in `lang/id/*.php` and `lang/id.json`, published by `laravel-lang/lang` (dev dependency; refresh with `php artisan lang:update`) and excluded from Pint. Validation attribute names (`kode`, `nama`, …) are in the `attributes` key of `lang/id/validation.php`; add new form fields there. Write app strings in Indonesian directly, e.g. `__('Profil diperbarui.')`.

**Dates and time.** Store UTC, convert only at the edges:

- `app.timezone` stays `UTC`; timestamps are stored and serialized (ISO 8601) in UTC.
- The display timezone is WITA: `DISPLAY_TIMEZONE` (`config('app.display_timezone')`, default `Asia/Makassar`), shared to the frontend as `displayTimezone`.
- Frontend display goes through `resources/js/lib/format.ts` (`useFormatDate()` in components): `25 Sep 2026 10:15`, `25 Sep 2026`. Never call `toLocaleString()` or `Intl` directly in components.
- Server-written text (toasts, later exports/PDF) uses `App\Support\DisplayDate::dateTime()`/`date()`, which produce the same strings.
- User-entered dates used as filters become UTC bounds through `DisplayDate::startOfDayUtc()`/`endOfDayUtc()` (see `ActivityLogController::index`), so a 07:30 WITA entry is found under its WITA day.
- Date-only values (e.g. future WO due dates) use `DATE` columns and are never timezone-converted.

**Flash toasts.** On the backend, call `Inertia::flash('toast', ['type' => 'success', 'message' => ...])`. On the frontend, `resources/js/lib/flashToast.ts` listens for the router `flash` event and shows the message with `vue-sonner`.

**Audit trail (spatie/laravel-activitylog v5).** Everything goes to the `activity_log` table, readable at Admin › Log Aktivitas (`Admin\ActivityLogController`, permission `activity-log.view`, admin only).

- **Model changes** (log `audit`): models use `App\Concerns\LogsModelActivity`, which logs created, updated, deleted, and restored with only the fillable attributes that changed. An update that flips `is_active` is logged as `activated`/`deactivated`. Override `activityLogOptions()` to ignore housekeeping columns (see `User`).
- **Changes model events can't see**, such as pivot syncs (a user's roles, a role's permissions): call `logAuditChange()` from `App\Concerns\LogsAuditChanges` with the state before and after. It logs only the keys that changed, in the same shape as model changes.
- **Auth events** (log `auth`): `App\Listeners\RecordAuthActivity` (event discovery) plus `App\Concerns\LogsAuthActivity` log login, logout, failed login (email tried and IP, no causer), password changes, and resets. Because each failed login writes a row, the `login` rate limiter caps attempts both per email+IP (5/min) and per IP (30/min).
- **Never log secrets.** `password`, `remember_token`, and the 2FA columns are excluded globally in `config/activitylog.php`. `Illuminate\Auth\Events\Failed` carries the typed password in `credentials`, so read only `email` from it.
- Event names and their labels live in `App\Enums\AuditEvent`, and subject labels in `App\Enums\AuditSubject`. `ActivityResource` turns an entry into labelled before/after rows.
- **Retention.** `activitylog:clean` runs daily (`routes/console.php`) and keeps `ACTIVITYLOG_CLEAN_AFTER_DAYS` days (default 365). Production needs the scheduler running (`schedule:run` in cron).

**Appearance (light/dark).** `components/ThemeToggle.vue` (app header and auth pages) flips light/dark; Settings › Tampilan also offers "Sistem". The `appearance` cookie is read server-side by `HandleAppearance` and client-side by `composables/useAppearance.ts`. The `appearance` and `sidebar_state` cookies are deliberately left unencrypted in `bootstrap/app.php` so the frontend can read them.

## Work Order module

A skeleton: the approval and execution flow is not designed yet. Out of scope so far: approval, execution stages, BAST, payment, notifications, and for comments @mentions, attachments, and a recipient field.

- **Status is PROVISIONAL.** `app/States/WorkOrder/` (spatie/laravel-model-states) holds every status and every allowed transition, in `WorkOrderStatus::config()`, and nothing else defines them. Today: Draft → Diajukan, Draft/Diajukan → Dibatalkan (a note is required). Each state carries its label, badge `tone` (docs/DESIGN.md), button label, and flags (`isEditable`, `assignsNumber`, `requiresNote`). The UI gets statuses from `WorkOrderStatus::options()` and each WO's available transitions from the server, so replacing the flow means editing that folder, the dashboard's "Menunggu Persetujuan" mapping (Diajukan), and tests.
- **Transitions** go only through `App\Actions\WorkOrders\TransitionWorkOrder`, which in one transaction locks the WO, assigns its number if the new status `assignsNumber()`, transitions, writes a `work_order_status_histories` row (from, to, user, note), and logs `AuditEvent::StatusChanged`. `status` and `number` are not fillable, so model events never log them twice. Creation writes the first history row (`null → draft`).
- **PROVISIONAL: who may transition.** `WorkOrderPolicy::transition` allows anyone with `work-orders.update` who can see the WO, until the real flow assigns transitions to roles.
- **Numbering.** A WO gets its number on submission (Draft → Diajukan), so deleted drafts leave no gaps; drafts have `number = null` and show "Draft" (`WorkOrder::displayNumber()`) in lists, detail, and activity log subjects. `App\Support\WorkOrderNumberGenerator` renders `config('work_order.number_format')` (`WO_NUMBER_FORMAT`, default `WO/{DEPT_CODE}/{YYYY}/{MM}/{SEQ:4}`, dates in WITA). The format with every token but `{SEQ}` filled in is the counter scope in `work_order_number_sequences`, locked with `lockForUpdate()`, so the default counts per department per month. `WorkOrderNumberConcurrencyTest` (group `concurrency`) proves no duplicates with parallel processes; it needs a shared PostgreSQL/MySQL database, is skipped on SQLite, and runs in CI as part of `composer test`.
- **Visibility.** Users see their own department's WOs; `work-orders.view-all` sees all. `WorkOrder::scopeVisibleTo()` filters lists and counts; `WorkOrder::isVisibleTo()` backs every record check in `WorkOrderPolicy`, which answers **404** (`denyAsNotFound`) for another department's WO. Form requests return `Gate::inspect(...)` so the 404 survives. A user without a department sees none and cannot create.
- **PROVISIONAL: initial `view-all` and `export` grants.** `RolePermissionSeeder::INITIAL_ROLES` gives `work-orders.view-all` and `work-orders.export` to `approver` and `keuangan` (fresh installs only; admins edit roles afterwards).
- **Rules.** A WO belongs to its requester's department (fixed at creation). Only drafts are edited or deleted (other statuses get an error toast; cancel instead). `target_date` is a `DATE`, must be today (WITA) or later only when set or changed, and is shown with `formatCalendarDate()` (never timezone-converted). Forms offer active, non-deleted categories plus the WO's current one.
- **Documents.** The `dokumen` attachment collection (`WorkOrder::DOCUMENTS`, limits in `config/work_order.php` → `attachments.dokumen`). PROVISIONAL: `WorkOrderPolicy::addAttachment`/`deleteAttachment` allow changes only on drafts, by anyone with `work-orders.update` who can see the WO; viewing and downloading follow `view`. The create form sends documents with the WO (`attachments[]`, same rules); Show and Edit upload immediately. Later stages (BAST, invoice) add their own collections in `WorkOrder::attachmentCollections()`.
- **List filters and sort.** `ListWorkOrdersRequest` validates the list's filters and builds its query (`workOrders()`: visibility, search, filters, order). `index` and the export both use it, so an export never holds more than the list shows, in the same order. Newest first by default; `sort=urgensi` (the "Urutkan" select) puts the most urgent first, then newest (`WorkOrderUrgency::orderMostUrgentFirst()`). The sort is not a filter: it does not trigger the "Tidak ada … yang cocok" empty state or appear in the export's logged filters.
- **Urgency.** `App\Enums\WorkOrderUrgency` (rendah, normal, tinggi, mendesak; column `urgency`, default normal). Set on the form (create and draft edit, like the other fields), filterable and sortable on the list, an Urgensi column in the export, and labelled in the activity log. Displayed only through `WorkOrderUrgency.vue` (docs/DESIGN.md › Urgensi Work Order). PROVISIONAL/OPEN: whether approvers may change urgency after submission; whether urgency should affect target dates or SLAs.
- **Excel export.** "Ekspor" on the list (`work-orders.export`, `WorkOrderExportController`, permission `work-orders.export` on top of `work-orders.view`) downloads the current filters as `WOrder-WorkOrders-<YYYYMMDD-HHmm WITA>.xlsx`, written by `App\Support\WorkOrderSpreadsheet` with openspout (streamed, header row frozen). Every text cell is built as a `StringCell`, never through `Cell::fromValue()`, which turns text starting with `=` into a formula; openspout's reader relabels such strings as formulas too, so tests check the sheet XML. Urgensi is its label. Timestamps are Excel date cells converted to WITA first (`d mmm yyyy hh:mm`); Target is a date cell, never converted (`d mmm yyyy`). Diajukan is the first `diajukan` status history row. Above `WO_EXPORT_MAX_ROWS` (default 5000) the export is refused with a toast asking to narrow the filters (the page checks too, from the list total). Each export logs `AuditEvent::Exported` (no subject; `filter`, `jumlah_baris`, `ip`). Exports are throttled to 10 a minute per user.
- **Comments.** `WorkOrderComment` (plain text, max 2000, `edited_at`, soft deletes; a plain FK, not polymorphic, so not in the morph map). Written only through `AddWorkOrderComment`/`UpdateWorkOrderComment`/`DeleteWorkOrderComment` (`app/Actions/WorkOrders/`), which re-read the WO under a shared lock and log `AuditEvent::CommentAdded`/`CommentEdited`/`CommentDeleted` on the WO (so they show in its Riwayat) with the author as causer and only `komentar_id`, never the text. Reading follows `view`. `WorkOrderPolicy::addComment`/`updateComment`/`deleteComment` build on `view()` (visibility 404, so a future recipient added in `isVisibleTo()` gets access with their role) plus the `work-orders.comment` permission; editing and deleting also need to be the author. Posting, editing, and deleting are each throttled to 10 a minute per user. Editing and deleting lock the comment row and refuse one deleted since the page loaded. The body is rendered by interpolation with `whitespace-pre-line`, never `v-html` or markdown.
- **PROVISIONAL: comment rules.** A status whose `acceptsComments()` is false (today Dibatalkan) keeps its comments read-only. Authors may edit or delete their own comment only within `config('work_order.comments.edit_window_minutes')` (`WO_COMMENT_EDIT_MINUTES`, default 15); edited ones show "(diedit)", deleted ones stay in the timeline as "Komentar dihapus". Both rules are enforced in the actions (`CommentNotAllowed` → error toast), not the policy, because an open page can go stale. `RolePermissionSeeder::INITIAL_ROLES` grants `work-orders.comment` to every initial role except `viewer` (fresh installs only).
- **Timeline.** The detail page's "Aktivitas" section (full width, below Dokumen) is `App\Support\WorkOrderTimeline`: status history and comments (deleted ones included) merged oldest first; at the same moment a status change comes first. Transition notes stay inside their status entry. `components/work-orders/WorkOrderTimeline.vue` renders it with the comment form at the bottom.
- **OPEN: Diajukan column.** It shows the first submission. When reject/resubmit exists, decide whether it should show the first or the latest.
- **Files.** Routes in `routes/web.php` (`work-orders.*`, `work-orders.export`, `work-orders.restore`, `work-orders.transitions.store`, `work-orders.comments.*` with scoped bindings); `app/Http/Controllers/WorkOrders/`, `app/Http/Requests/WorkOrders/`, `WorkOrderResource`; pages in `resources/js/pages/work-orders/`, components in `resources/js/components/work-orders/`, types in `types/workOrder.ts`, badge classes in `lib/workOrderStatus.ts`.

## Attachments

Files on any model, through spatie/laravel-medialibrary. Work orders are the first user (see above).

- **Making a model attachable.** Implement `App\Support\Attachments\Attachable`, use `App\Concerns\HasAttachments`, and declare `attachmentCollections()`: one `AttachmentCollection` per collection (name, `maxFiles`, `maxSizeKb`, optional subset of `AttachmentType`s), with limits read from that module's config. The model must be in the morph map. Its policy needs `addAttachment(User, Model, string $collection)` and `deleteAttachment(User, Model, Media)`, both starting with the model's visibility check; reading uses its `view`. Pass `AttachmentPanel::props($model, $collection, $user, $request)` to the page and render `components/attachments/AttachmentPanel.vue`; nothing else is model-specific.
- **Where the rules live.** Allowed types: `App\Enums\AttachmentType` (PDF, JPG, PNG, WEBP, DOCX, XLSX). SVG, HTML, and macro-enabled Office files are deliberately not cases, so no collection can accept them. `App\Support\Attachments\AttachmentTypeDetector` identifies a file by content (finfo), never by its name or the client's MIME type; for ZIP-family results it opens the package and accepts only a single `docx`/`xlsx` main part and no `vbaProject.bin` (libmagic reports docm/xlsm as docx/xlsx). Validation is `AttachmentCollection::fileRules()` (size + `App\Rules\AllowedAttachment`); `App\Actions\Attachments\AddAttachment` re-detects the type and checks the file count with the parent row locked, before anything is stored. It registers `DB::afterRollBack()` to delete the stored file, so a rollback in its own or the caller's transaction (e.g. `WorkOrderController::store` with several documents) leaves no orphan; a PHP process killed mid-request can still leave one, and there is no sweep job yet. Uploads are throttled to 30 a minute per user.
- **Private disk only.** Files go to the `attachments` disk (`storage/app/attachments`, no URL, `serve => false`; `MEDIA_DISK`). They are stored as `{media uuid}/{random uuid}.{detected ext}` (`AttachmentPathGenerator`); the original filename is kept only in `media.name`, for display and the download name. `media.mime_type` is the detected type and `media.uploaded_by` the uploader. Never generate a URL on the disk or use media-library's `getUrl()`.
- **Every file goes through `AttachmentController`.** `attachments.store` (`POST attachments/{alias}/{id}/{collection}`) resolves the parent by morph alias (404 unless it is `Attachable` and has the collection) and authorizes `addAttachment`; `attachments.show` (`GET attachments/{uuid}`) authorizes the parent's `view`, so department visibility gives 404, and a deleted parent gives 404; `attachments.destroy` authorizes `deleteAttachment`. `show` sends the detected `Content-Type`, `X-Content-Type-Options: nosniff`, and `Cache-Control: private, no-store`; images and PDF are `inline` (unless `?download=1`), everything else is `attachment`.
- **Audit.** `AddAttachment`/`RemoveAttachment` log `AuditEvent::AttachmentAdded`/`AttachmentRemoved` on the parent with `lampiran` (filename) and `ukuran` (bytes, shown as "1,6 KB"), never file content. `Media` does not use `LogsModelActivity`. Soft-deleting the parent keeps its files; only a force delete (never offered) would remove them.
- **Upload limits.** The size limit only works if PHP's `upload_max_filesize` and `post_max_size` and the web server's body limit (nginx `client_max_body_size`) are at least as large; `post_max_size` must also fit a create form with several documents (e.g. 10 × 10 MB). `MEDIA_MAX_FILE_SIZE_MB` (default 50) is media-library's hard ceiling above every collection limit.
- **Tests.** Fixtures in `tests/Fixtures/attachments/` (real files, excluded from formatting); `attachmentUpload($fixture, $clientName)` in `tests/Pest.php` disguises one type as another. Fake the disk with `Storage::fake('attachments')`.

## Master data module pattern

`Department` is the reference implementation. New master data (WO categories, vendors, etc.) copies it file for file. `User` follows the same rules with extra account logic.

- **Active vs deleted.** `is_active = false` means deactivated: the record stays in lists with a `StatusBadge` and can still be referenced. Soft delete (`SoftDeletes`) hides it from lists and dropdowns. It shows up only under "Tampilkan terhapus", which needs `*.restore`, with a Pulihkan action (`PATCH <resource>/{id}/restore`, route `->withTrashed()`). The UI never force-deletes. **Relationships from other modules to master data use `->withTrashed()`** so history still resolves.
- **Unique vs trashed.** Unique indexes still cover deleted rows. Use `Rule::unique(...)->withoutTrashed()` plus `App\Rules\NotTakenByTrashed`. That rule shows the "pulihkan" hint only to users who can `viewTrashed`, and everyone else gets the standard "taken" message. See `app/Concerns/DepartmentValidationRules.php`.
- **Delete guards.** Refuse deletes that would orphan live data with an error toast and `back()`, not an exception. Example: `DepartmentController::destroy` refuses while `$department->users()->exists()` and suggests deactivating instead.
- **Audit trail.** The model uses `LogsModelActivity` (and gets a morph alias, see Conventions). Controller writes that model events miss, such as pivot syncs, call `logAuditChange()`. Add the alias to `AuditSubject` (and to `withHistoryPanel()`), the label of any new attribute to `ActivityResource::FIELD_LABELS`, and new event names to `AuditEvent`. Index rows get a "Riwayat" icon button (`History`, shown with `useCan()('activity-log.view')`) that opens the shared `components/admin/ActivityHistorySheet.vue`.
- **Permissions and policy.** Add `App\Enums\Permission` cases `<resource>.view|create|update|delete|restore` (kebab-case plural resource). `app/Policies/DepartmentPolicy.php` maps them as follows: `viewAny`→`view`, `viewTrashed`/`restore`→`restore`, and `forceDelete` returns `false`. Every check uses `$user->checkPermissionTo(...)`.
- **Seeder.** `database/seeders/RolePermissionSeeder.php` creates every enum case with `findOrCreate`, calling `forgetCachedPermissions()` before and after (without the second call, `syncPermissions` can't see the new permissions). It then syncs `admin` to all permissions. Grants for other roles go in `INITIAL_ROLES`, which only applies when the role is first created.
- **Backend files.**
    - Model with an `inactive()` factory state and a `#[Scope] search` via `SearchesColumns`: `app/Models/Department.php`.
    - Shared rules trait: `app/Concerns/<Resource>ValidationRules.php`.
    - `Store`/`Update<Resource>Request` in `app/Http/Requests/Admin/`, with `authorize()` via the policy.
    - `app/Http/Controllers/Admin/<Resource>Controller.php`: `index` validates the filters, requires `viewTrashed` for `trashed=1`, returns `paginate(15)->withQueryString()` plus a `can` map; the other actions flash a toast.
    - Routes in `routes/admin.php`.
- **Frontend.**
    - Page: `resources/js/pages/admin/<resources>/Index.vue`, with `PagePanel`, `ListToolbar`, `ClickableRow` + `RowActionsMenu`, a group crumb plus its own crumb, and `EmptyState` for both empty cases (no `StatStrip` unless its numbers are useful). Small forms use a dialog in `components/admin/` (`DepartmentFormDialog.vue`); large forms use `Create`/`Edit` pages sharing a form component (`UserForm.vue`).
    - Filters: `composables/useListFilters.ts` (debounced search, `ALL` sentinel for selects, booleans sent as `1`).
    - Table: `components/ui/table`, `components/admin/TablePagination.vue`, `StatusBadge.vue`, and `ConfirmDialog.vue` for deletes.
    - Types go in `types/admin.ts`, and the sidebar entry in the right `navGroups` group of `AppSidebar.vue` with a `permission`.
- **Required Pest tests** (see `tests/Feature/Admin/DepartmentControllerTest.php`):
    - Search, filter, and pagination.
    - Deleted rows hidden by default, and the deleted list forbidden without `restore`.
    - Create/update happy path plus validation.
    - Unique conflict with a deleted row, both with and without the restore permission.
    - Soft delete, the delete guard, and restore.
    - A dataset proving each endpoint returns 403 without its permission, using the `userWithPermissions()` helper.
    - The model in the `logged models` dataset of `tests/Feature/ActivityLog/ModelActivityTest.php`.

## Conventions and gotchas

- **Morph map is enforced** (`Relation::enforceMorphMap()` in `AppServiceProvider`). Polymorphic columns (`model_has_roles`, `model_has_permissions`, `activity_log`, `media`) store short aliases such as `user` and `wo-category`, not class names. Every model used polymorphically must be registered there, or it throws `ClassMorphViolationException`. In tests, compare against `$model->getMorphClass()`, not `Model::class`.
- **Rate limits: always a named limiter, never a plain `throttle:N,1`.** A plain `throttle:N,1` keys only on the user, so every route using one shares one counter (10 uploads used to block the export). Define each limiter with `RateLimiter::for()` in `AppServiceProvider::configureRateLimiting()` (Fortify's `login` stays in `FortifyServiceProvider`) and attach it as `throttle:<name>`; today `password-update`, `wo-export`, `wo-comment-post`, `wo-comment-change`, `attachment-upload`. `tests/Feature/RateLimitingTest.php` fails if any route uses a plain `throttle:N`.
- `resources/js/components/ui/*` is generated shadcn-vue code (`components.json`). Lint and format both ignore it, so add or replace components with the shadcn CLI instead of restyling them by hand.
- Rector (`rector.php`) deliberately skips `declare(strict_types=1)`, and skips `: void` on closures in `tests/`. The codebase doesn't use strict_types, so don't add it.
- PHPStan covers `app/`, `config/`, `database/`, `routes/`, and `bootstrap/app.php`. It does not cover `tests/`.
- **PHP 8.4 or later is required, including production.** `openspout/openspout` ^5 (the Excel export) needs it. PENDING: the production PHP version is not confirmed yet; if it is 8.3, switch to openspout ^4 and lower `composer.json`'s `php` constraint back to `^8.3`.
- The database is **PostgreSQL** in every environment. Locally it's the shared `postgres-dev` container from `~/Workspaces/databases/docker-compose.yml` (`docker compose up -d postgres` there), with the databases `work_order` (dev) and `work_order_test` (tests; set in `phpunit.xml`). CI runs a `postgres:16` service, and production uses its own server. Postgres `LIKE` is case-sensitive, so search through `App\Concerns\SearchesColumns` (ILIKE with escaped wildcards) instead of a raw `where(..., 'like', ...)`.
- Feature tests use `RefreshDatabase` through `tests/Pest.php`, so Postgres must be running before `composer test`.
- **KNOWN ISSUE: SSR hydration warnings.** Pages log Vue hydration mismatches in the browser console: reka-ui's generated dropdown IDs differ between server and client (e.g. `reka-dropdown-menu-trigger-v-7` vs `-v-0`, on the avatar menu and every `RowActionsMenu`), and the sidebar toggle icon's path differs (the server can't know the sidebar/viewport state). They are check-only (the DOM isn't patched) and predate the comments feature; not fixed yet.
- `.npmrc` sets `ignore-scripts=true`, so npm packages' install scripts don't run.
